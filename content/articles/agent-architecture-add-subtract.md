# Agent 架构的加减法:复杂度该花在边界上,而不是层级上

> 一句话结论:**Agent 架构的复杂度,应该按「边界」分配,而不是按「角色」分配。** 一个任务能装进一个上下文窗口,就把子智能体折叠回主循环,用 Skills 和 Tool Search 做渐进式披露;只有当上下文必须隔离、任务必须并行、会话必须跨天存活时,才为第二层付费。而且无论加还是减,边界都要写进结构,不能写进提示词。

---

> **🧭 为什么要收录这两篇**
>
> Anthropic 应用 AI 团队复盘企业级 Agent 部署后发现:把 Router、Planner、领域子智能体折叠进一个主循环,质量、成本、延迟常常同时变好。一周多以后,DeepSeek Harness 团队公开 Super-agent 设计:用一个常驻 Router 管多个隔离 Worker,把会话调度抬到系统层。
>
> 一篇在删层级,一篇在加层级,读起来像互相打脸。但把它们放在一起,恰好拼出一张完整的判断表:**什么时候该折叠,什么时候该分层。**

---

## 一、两篇文章,两个相反的动作

### Anthropic:把子智能体折叠回主循环

Anthropic 的结论说得很直白:在多组企业部署的对比里,**「单 Agent + Skills」在质量上经常胜过「一个 prompt 打天下」,也胜过「orchestrator + 子智能体」**,而且往往每个任务的成本、延迟更低。

反面案例也很具体:一家公司在面向用户的客服系统里塞了十几个专家子智能体,结果品牌语气难以统一,延迟直接把体验毁掉;另一家把多智能体框架拆回单循环后,运行速度快了约 2 倍。

拆开看,多智能体的病灶不是「多」,而是**每一次交接都是一次有损压缩**——文章把它叫「电话游戏」:

- **上下文丢失**:主 Agent 把任务摘要传给子 Agent,子 Agent 干完再还一份摘要,细节在来回倒腾中消失。
- **子智能体泛滥**:每个团队交一个,几个月后长出几百个没人统一标准、功能高度重叠的野生 Agent。
- **缝补怪提示词**:每个业务方都要求「在主 prompt 里加一句我们的规则」,最后主 prompt 逻辑自相矛盾、语气精神分裂。
- **局部刷分**:每个团队只优化自己那亩三分地的 eval,局部准确率 99%,用户一用端到端流程就崩。
- **延迟叠加**:多一层编排,就多一次模型调用。

替代方案是**单循环 + 渐进式披露**:一个模型、一个上下文窗口,每轮发一批工具调用,harness 并行执行后把原始结果还给同一个模型;计划写在上下文里,由执行任务的模型自己改。业务流程、领域 SOP 收进 Skills;调接口、查数据收进 MCP Tools,配合 Tool Search 按需加载;硬性校验、权限、审批门禁放进 Tool 内部。Anthropic 说,他们已经把 Claude Code 在高阶模型下的系统提示词砍掉了 80% 以上——其中就包括渐进式披露带来的删减。

但这不是「放弃 Multi-Agent」。文章明确了子智能体仍然值得保留的三种情况:

1. 单循环因为上下文膨胀,出现了**可测量**的性能下降;
2. 多个任务必须并行,且每一路的上下文用完即弃;
3. 单循环在工具太多时选不明白,或者系统提示词里出现了互相冲突的指令。

### DeepSeek:把会话调度抬到系统层

DeepSeek 要解决的不是「单个任务做不好」,而是**多任务的天花板是人的注意力**。主流 Agent 的工作单位仍然是单次会话:一个人同时推进几件事,就得手动开几个 Session,来回切换,还要自己记住每个 Session 里说过什么。团队给出的观察是,一个人通常只能同时跟进 3 到 5 个活跃会话。模型越强,这个矛盾越尖锐。

Super-agent 的解法是双层:

- **Router**:常驻的全局协调节点,接群聊、GitHub、邮件等多渠道消息,识别任务归属并分派,维护跨任务上下文,统一对外回复。它不执行具体任务,**甚至可以不配 Bash 工具**。
- **Worker**:一组相互隔离的会话,各自维护独立上下文,并行执行复现、审查、开发等具体工作。挂完整工具链、通常配最强模型,但**不直接与人类交互**,结果汇报给 Router,由 Router 统一说话。
- 任务被组织成 **Ticket**:每个任务有自己的执行会话与目录,进度和讨论可以延续,人不再用聊天窗口的位置来记事情。

支撑这套双层结构的,是五组很「操作系统」的模块:事件驱动(Trigger + Fast/Slow Path 两级过滤 + Thread 订阅)、持久在线(计算/状态/执行环境分离 + 独立 Watchdog)、异步 ReAct(长任务不阻塞对话)、投机执行(静默复现并修复,宁可白干不打扰)、上下文管理(Inline & Spill + Chain of Recall)。

它也付得起账的证明,来自一组粗略数字:在约 300 条消息、20 项工作请求的模拟环境里,**P95 完成时间约为单 Session 方案的一半**;而代价是更多 token——去掉订阅直通后,Router 决策次数增加约 30%,读缓存 token 从 2323 万涨到 3177 万(约 +37%)。一句话:**拿 token 换时间与稳定性。** 团队自己也标注了这是合成负载、简化环境下的初步结果。

所以这两篇文章的真实关系是:**Anthropic 在删「任务内部」的层级,DeepSeek 在加「任务之间」的层级。**

## 二、不是打架,是在算两本账

| | Anthropic 的账 | DeepSeek 的账 |
|---|---|---|
| 优化对象 | 单个任务的端到端质量、成本、延迟 | 多个任务的并发、连续、恢复 |
| 层级买到了什么 | 几乎没有,交接反而有损 | 隔离、并行、长期在线 |
| 层级的代价 | 延迟、上下文丢失、治理成本 | token、系统工程、复杂度 |
| 结论 | 能装进一个窗口就折叠 | 跨会话调度必须抬到系统层 |

这两本账其实问的是两个不同维度的问题:

**空间维度(上下文)**:完成一次任务所需的信息,能不能装进一个窗口?装得下,多一层就是多加一道有损压缩;装不下,先试渐进式披露,只有「必须整个丢掉」的并行支线才值得开新窗口。

**时间维度(会话)**:一个人的工作是不是跨多个渠道、多天、多个任务?是,就需要一个常驻的协调层。否则那个人脑就是 Router——而且是会遗忘、切换成本极高的 Router。

两个极端都被否掉了:

- **所有消息进同一个会话**:上下文连续,但执行串行阻塞,不同任务的细节互相污染。
- **每条消息开一个会话**:并发好做,全局协调和交互一致性又丢了。

所以「几个 Agent」从来不是问题,「边界在哪」才是。**层级不是免费的,它买的是边界。** 买不到边界的层级,就是汇报 PPT 上的工业美学。

## 三、同一条底层原则:把约束从提示词搬进结构

两边最像的地方,不是都用 Agent,而是都**不指望模型临场自觉**。

Anthropic 的做法:

- 把权限和前置校验塞进 **Tool 内部**:越权就返回一句大白话让模型自己圆场,而不是给每个权限等级建一个 Agent。
- 工具按「用户意图」聚合,不按 API 拆:上下文里的工具定义一旦超过 30–50 个,模型挑工具就会挑花眼。
- 一个极小的中央团队独占 system prompt 与端到端评测,任何新 Skill / Tool 必须过准入检视。

DeepSeek 的做法:

- **Router 不装 Bash**:不是「提示它别执行」,而是让它没有执行能力。
- **Worker 不直接对人说话**:对外口径只留一个出口。
- **Thread 订阅只提供信息**,不自动赋予新权限,超出当前任务范围的要求仍要重新走分派。
- **Mandate 限定每个任务的授权范围**,防止 Agent 擅自扩权。

两种做法可以压成一句话:**可靠性来自「做不到」,不来自「说好了」。**

这和本站 [第 23 讲:规格即架构约束怎么写给 AI](../tutorial/23-规格即架构约束怎么写给AI.md) 是同一个判断:写进结构的约束是硬约束,写进提示词的约束是建议。Agent 系统里的每一个「它应该不会……」,最后都要么变成结构,要么变成事故。

## 四、减法也要先证明自己

折叠听起来是「删代码」,实际上是最容易翻车的手术。两篇文章给的是同一味药:**先有基线,再动结构。**

Anthropic 的四步走:

1. **先立评测**:一个中央团队拥有的端到端评测集,加上每个 Skill 自带的小评测;10 个黄金用例就够起步。指标从「路由准不准」换成「问题解决得怎么样、有没有加载对的 Skill 和 Tool」。
2. **合并连体婴**:生产日志里如果 A 执行完十有八九紧跟着调 B,或者两者总读写同一份数据,它们就该合并。
3. **降级为 Tool**:复杂的子智能体先不拆,包成 Tool 让主 Agent 调,主 Agent 始终拿着麦克风;只有必须直接跟用户多轮对话时,才做全量交接。
4. **逐个折进 Skill 和 Tool**:一个接一个地折,折一个比一次。

代价长什么样?文章给了一个真实案例:一个客服 Agent 折叠后延迟降了、总分也不错,但**原本通过的一个核心流程挂了**——主 Agent 拿到「查订单」工具后自己拍脑袋答复,忘了按规矩再问物流专家的发货日期。而且这种偶发 bug 跑两次才复现一次。所以规则是:**盯 Pass→Fail 的翻转用例,每个任务多跑几遍,别只看总分。**

DeepSeek 的做法在方法论上是同构的:主动接活默认是**观察模式**——先记录「本来会接什么任务」,跑一段时间确认推断可靠,再放开自动执行;投机执行也是先算后说,没价值就静默丢弃。

这里有个共同的判断值得单独拎出来:**评测不是交付前的关卡,是架构的仪表盘。** 没有基线的重构,不是架构优化,是拿生产环境做审美实验。多智能体结构的失败,很少以「分数下降」的形式出现,而是以「某个流程偶发断裂」的形式出现——这正是 [第 25 讲:评测驱动,把「够好」写进架构](../tutorial/25-评测驱动把够好写进架构.md) 想解决的问题。

## 五、一张可以带走的决策表

| 你观察到的信号 | 该做的事 | 为什么 |
|---|---|---|
| 一个任务的信息装得进一个窗口 | 折叠成单循环 | 交接是有损压缩,多一层多一道损耗 |
| 只是步骤多、规则多 | 用 Skills 渐进披露 | 规则是知识,不该占 prompt 常驻空间 |
| 工具多到模型选不明白 | 按意图聚合 + Tool Search | 30–50 个工具定义后选择质量下降 |
| 不同权限的人共用一个入口 | 把权限判断放进 Tool | 不必为每个权限等级建 Agent |
| 两条支线必须并行,且上下文用完即弃 | 保留子智能体 / Worker | 隔离是真实存在的边界 |
| 任务是验证型的(生成→校验) | 保留生成-验证分工 | 独立判断比自我检查可靠 |
| 工作跨天、跨渠道、必须在线 | 需要常驻协调层(Router) | 人脑不适合当调度器 |
| 任务之间互相污染、串行阻塞 | 拆隔离会话 + 订阅路由 | 上下文隔离是硬需求 |
| 交接频繁且每次都丢细节 | 合并,或直接折叠 | 有损压缩的代价超过了隔离收益 |

再把流程收成一句:**合并连体婴 → 降级为 Tool → 折进 Skill / Tool → 只保留验证器。** 每一步只改一个变量,跑完评测再走下一步。

## 六、组织形状,会复制进 Agent 形状

Anthropic 把话说明白了:企业给每个团队、每类问题各配一个子智能体,Agent 架构就变成了组织架构图的复印件——这就是康威定律。行政上最省事:每个部门领 KPI 回去闭门造车,平台团队在顶上糊一个 Orchestrator。工程上却是灾难:野生子智能体、缝补怪提示词、局部刷分。

他们给的解不是「再包一层编排」,而是**把组织边界改造成知识边界**:

- 一个极小的中央团队,死守唯一的 system prompt 和端到端评测,新 Skill / Tool 必须过准入;
- 各业务线不再造 Agent,转型做「军火商」,专门维护自己领域的 Skills、MCP Tools 和知识库。

这和本站 [第 15 讲:组织即架构](../tutorial/15-组织即架构.md) 是同一个旋律:系统会长得像你的组织。区别在于,以前是「团队边界决定服务边界」,现在多了一层选择——**团队边界可以直接变成 Skill / Tool 的所有权边界,而不必变成 Agent 边界。** 少一层 Agent,就少一份需要协调的上下文和对外口径。

DeepSeek 的 Router / Worker 是同一件事的另一面:它没有按业务领域切 Agent,而是按**职责**切——协调的只协调,执行的只执行,并且把这个边界焊死在结构与工具清单里。两边都在回答同一个问题:**当组织必然要分裂时,应该让它在哪一层分裂。**

## 七、对我们的启发

### 对课程:三个可以直接引用的注脚

- [第 22 讲:AI 原生系统设计](../tutorial/22-AI原生系统设计.md):自主性每涨一格,非确定性、成本、上下文三个约束就放大。这两篇文章是「自主性该涨到哪一格」的最新注脚。
- [第 35 讲:AI 原生组织架构](../tutorial/35-AI原生组织架构.md):「小中央团队 + 业务线做 Skills」就是组织级 AI 杠杆的一种具体形态,也是「AI 原生」从口号落到职责表的样本。
- [第 09 讲:架构品味](../tutorial/09-架构品味.md):真正的架构师敢删。Super-agent 这类系统级设计也提醒我们:Agent 的下一程竞争,可能不在模型榜单,而在谁先把「操作系统」那一层做扎实。

### 对团队:五条可以马上执行的规则

1. **新项目默认从单循环起步**:一个清晰的 system prompt + 4–5 个薄工具 + 输出护栏。先证明它不够用,再加层。
2. **复杂度花在「能力外置」上**:Skills(怎么做)、Tools(能做什么)、知识库(知道什么),而不是「人格」和「角色扮演」。
3. **任何人提「加一个 Agent」,先让他给出一个失败用例**:是上下文溢出、并行需求,还是权限隔离?给不出,就是组织图在说话。
4. **建 10 个端到端黄金用例**,归中央团队所有;每次结构变更盯翻转用例,每个任务多跑几遍。
5. **涉及主动行为**(自动接活、自动修复),先跑观察模式,用日志证明推断可靠,再放开执行。

### 对个人:多开 Agent 多数时候是注意力税

- 你能同时跟进的活跃会话就是 3–5 个。超过这个数,切换成本会吃掉并行收益。
- 个人最高杠杆的形态往往是:一个主循环 + 一组好工具 + 清晰的验收标准 + 一个能长期保存上下文的记录,而不是十个聊天窗口。
- 判断自己该不该用多 Agent,只问一句:这些任务之间,有没有一个**必须隔离**的边界?

## 八、别急着下结论:三处要打折

1. **立场**:Anthropic 在推 Claude Platform 的 Skills / Tools 生态,DeepSeek 在推自己的 Super-agent 原型。两篇都是高质量的工程文章,但都不是中立评测。读架构文章,要顺手读一下「谁在为什么付费」。
2. **证据强度**:Anthropic 的「2 倍」来自单个客户的对比,「Claude Code 砍掉 80% 提示词」说的是自家产品;DeepSeek 的实验基于约 300 条消息、20 项请求的合成负载与简化环境,团队自己标注为初步参考。方向可信,数字别当定律。
3. **单循环的隐性成本**:折叠不是「什么都不做」。它要求更克制的 system prompt、更讲究的 Skill / Tool 描述、更自觉的上下文与记忆管理。折叠失败的表现也不是「总分掉」,而是偶发的流程断裂。

还有一条边界要守住:**折叠不等于消灭验证**。独立验证器、并行研究、权限隔离,仍然是子智能体最正当的三个理由。两篇文章都没有否定多智能体,否定的只是「把组织图抄进架构」。

## 九、把两篇压成一句话

> **单任务收敛,多任务分层;能装进一个窗口的,别开第二个窗口;非开不可的,就把边界焊进结构,并用评测证明它值这个 token。**

如果再往下压一层,是三个问题:

1. **边界在哪?** 上下文、生命周期、权限、并发——哪一个真实存在,并且测得出代价?
2. **能力放哪?** 是常驻 prompt、Skill、Tool,还是知识库?越靠后越省上下文,也越依赖好的描述。
3. **谁来验收?** 评测集、观察模式、翻转用例——没有度量,加减都只是审美。

模型每强一档,这套判断就要重算一遍。真正顶级的 Agent 架构师,不是把图画得最复杂的人,而是敢随着模型进化,不断把代码和层级删掉的人。
